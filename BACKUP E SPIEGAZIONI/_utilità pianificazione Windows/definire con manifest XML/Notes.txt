The XML is the complete definition of a Windows scheduled task. It is the internal “manifest” that Task Scheduler uses to know when, with which privileges, and how it must launch something. It is a snapshot of the state of a task named "FolderSyncWatcher".

Windows executes this XML every time it loads the task’s configuration. The resulting behavior is the following.

The task starts automatically. It is started in two cases:
		• at system startup (BootTrigger)
		• at user logon (LogonTrigger)

The PC doesn’t wait for you to open the session: as soon as Windows starts, it runs. And when you log in, it is restarted if necessary. It is executed with the highest available privileges:

		<RunLevel>HighestAvailable</RunLevel>

This means it doesn’t require admin rights, but if the logged-in user has elevated rights, the task inherits those privileges. This allows to access removable drives, read volume metadata, write logs where elevated permissions would normally be required. The task runs a minimized CMD window. Under "Actions" it is called:

	cmd.exe /c start "FolderSyncWatcher" /min /d "<watcher_folder>" "start_watcher.bat"

Briefly decoding it:
• cmd.exe /c = execute and then close
• start "FolderSyncWatcher" = open a new window with that title
• /min = open it minimized
• /d "<folder>" = set that directory as the working dir
• "start_watcher.bat" = execute the batch (which then launches Python and your watcher)

Windows executes start_watcher.bat in a CMD window that starts already minimized, so the user has not to see it pop up at every boot.

The power settings block the task if the PC is on battery. Since the XML contains:

		<DisallowStartIfOnBatteries>true</DisallowStartIfOnBatteries>
		<StopIfGoingOnBatteries>true</StopIfGoingOnBatteries>

If the PC is on battery, the task does not start while if the PC switches from AC to battery the task is stopped immediately. For a watcher that must monitor and synchronize files this can be reasonable, but it is a restrictive choice.

The task stays active without time limits. The parameter <ExecutionTimeLimit>PT0S</ExecutionTimeLimit> means: no timeout. The watcher can run for days without Windows interrupting it.

It doesn’t require network or idle conditions. This is because it is explicitly declared:

		<RunOnlyIfNetworkAvailable>false
		<RunOnlyIfIdle>false

It runs anyway, in any condition, except when the PC is on battery.

________________________
Root <Task>
________________________

Defines a Windows scheduled task.
Namespace and version indicate only the Microsoft standard being used.

________________________
<RegistrationInfo>
________________________

“Identity” information.

• Date — ISO8601 timestamp of task creation.
• Author — the account that created it (PC-ALESSIO\Utente).
• Description — human-readable description: “Custom watcher…”.
• URI — internal logical path in Task Scheduler. It is not a file path; the service uses it only to organize tasks.

________________________
<Triggers>
________________________
Conditions that trigger the task.

• <BootTrigger> Enabled=true — starts automatically at every system boot.
• <LogonTrigger> Enabled=true UserId=PC-ALESSIO\Utente — also starts when that specific user logs in.

This means the watcher is launched both at machine startup and when the user logs in, even if the machine was already on.

________________________
<Principals>
________________________

Who runs the task and with what privileges.

• UserId = SID of the user “Utente” — Windows uses the SID as an internal identifier.
• LogonType = InteractiveToken — uses the user session token; the task requires the user to be logged in.
• RunLevel = HighestAvailable — requests the highest available level (effectively “Run as Administrator” if the user is admin).

The watcher therefore runs with elevated privileges, but only in the user’s session.

________________________
<Settings>
________________________

Scheduler engine behavior parameters.

• MultipleInstancesPolicy = Parallel
If the watcher is already running and a trigger occurs, Windows launches another instance in parallel.
This can be risky for non-idempotent scripts but is often intended for file-based watchers.

• DisallowStartIfOnBatteries = true
• StopIfGoingOnBatteries = true
The task does not start (and is stopped) when the PC is on battery.
No effect on desktops; on laptops, yes.

• AllowHardTerminate = true
Windows can kill the process if needed (force termination).

• StartWhenAvailable = true
If a trigger was missed (e.g., PC off), the task starts at the first available opportunity.

• RunOnlyIfNetworkAvailable = false
Network is not required.

• IdleSettings → StopOnIdleEnd = true
But RunOnlyIfIdle = false, so the task does not actually depend on idle state.

• Enabled = true
• Hidden = false
• WakeToRun = false — does not wake the PC from sleep.
• ExecutionTimeLimit = PT0S — no duration limit (can run indefinitely).
• Priority = 7 — low priority (range 0–10). Used to avoid CPU overload.

________________________
<Actions>
________________________

What is actually executed.

The action is:

Command: C:\Windows\System32\cmd.exe
Arguments: /c start "FolderSyncWatcher" /min /d "C:\Users\Utente\OneDrive - Intrawelt S.a.s\Documenti - IT\Cybersec & IT Governance\_ 🧰 Resources\folder-sync-watcher" "start_watcher.bat"

At every PC startup (or user login), a minimized console runs in the background executing the start_watcher.bat script in the synchronized documents folder.
